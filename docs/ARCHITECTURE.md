# Architecture

**OpenStitch** runs on macOS, Windows and Linux. It is a Rust Cargo workspace: an embroidery
engine plus one cross-platform desktop app (egui/eframe on wgpu: Metal on macOS, DirectX 12 /
Vulkan on Windows, Vulkan/GL on Linux), following PhotoCraft's engine-first design. There is
no web runtime.

**Golden regressions:** `examples/badge.json` must keep exporting the recorded
`badge-golden.pes` byte for byte (`script_output_matches_golden_pes`), and the recorded
`badge-golden.osd` must keep compiling to the recorded statistics (`golden_badge.rs`).

Rules: `#![forbid(unsafe_code)]` workspace-wide; clippy with `-D warnings`; workspace members
are listed explicitly so a crate under construction never breaks other builds. Engine-side
runtime dependencies are only `serde`, `serde_json`, `ttf-parser` (see Lettering) and `i_overlay`
(shape operations, see Decisions);
`openstitch-mcp` adds `tiny-skia`, `png` and `base64`, all pure Rust; `openstitch-remote` adds
`getrandom` (the OS random source, for the socket token).

**CI and delivery** (`.github/workflows/`; packaging details in [DISTRIBUTION.md](DISTRIBUTION.md)):

- `rust.yml` runs fmt, build, test and clippy on macos-latest, windows-latest and ubuntu-latest
  for every pull request and every push to `main`. The ubuntu-latest job then runs the
  compatibility specs (`stitchtool compat --check-status docs/COMPATIBILITY_STATUS.md`). It
  uploads the report as the `compat-report` artifact.
- On `main`, it then calls `build-executables.yml`, which builds `openstitch`, `stitchtool` and
  `openstitch-mcp`: universal arm64 + x86_64 via `lipo` on macOS, x86_64 on Linux and Windows.
  It smoke-tests them with `stitchtool exec examples/badge.json` and packages them with
  `packaging/`: `OpenStitch.app` (zip) on macOS, zip + MSI on Windows, a tarball with
  `install.sh` on Linux, plus a CLI archive per OS. Each OS gets one 30-day workflow artifact.
  The same workflow also runs on pull requests that change packaging.
- `release.yml` runs only for a `vX.Y.Z` tag that matches the workspace version and sits on
  `main`; it re-runs the tests, builds and creates a draft GitHub release.
- Work goes through branches and pull requests. Tags are pushed only when the owner declares a
  version stable.

## Data model

- Contours: `points` plus optional `curves[i]` (cubic control points for the segment from vertex
  `i` to `i + 1`, the last one closing a closed contour). `curves` is omitted from JSON when no
  segment is curved, so straight-only designs serialize exactly as before. Stitch generators and
  scanlines use the flattened outline; running and triple stitches keep every vertex and split
  curved segments at equal arc length (straight segments keep the original equal split, so
  golden outputs are unchanged).

- `StitchPattern` is the machine-level interchange format: absolute 0.1 mm coordinates,
  y down, commands `stitch | jump | trim | colorChange | stop | end`, a thread per colour block.
- `Design` is the editable model (shape and stitch objects with sewing attributes). It compiles
  to a `StitchPattern`; codecs never see editable objects (the PES object section will get its
  own mapper).
- `.osd` project files are JSON: `{"format": "openstitch.design", "version": 1, "design": …}`.
  `serde_json` is built with `float_roundtrip`, so a saved design reopens bit-identical.

## Lettering

- A text object (`kind: "text"`) keeps a `text` spec — string, font id, size (mm), letter
  spacing (mm), line spacing (% of the character height, plus an older mm offset), alignment, optional `path` object id, a placement
  `transform` and per-glyph contour counts — plus the laid-out glyph `contours`, so drawing,
  hit-testing, bounds, transforms and hole sewing treat it like a shape. Every field added for
  text is omitted from JSON when unused, so shape-only `.osd` files are byte-identical and old
  files load unchanged.
- Layout: `ttf-parser` returns each glyph outline; TrueType quadratic segments become exact
  cubic Béziers (handles at 2/3 towards the quadratic control point). Inner contours (counters
  of o, B, 8) are holes under the even-odd fill rule. The compiler fills each glyph as its own
  region, letter by letter, so script joins that overlap never punch holes into each other.
- Transforms compose onto the text's `transform`, so changing the string or font keeps the
  placement. Text on a path walks the first contour of a shape object by arc length, centring
  each glyph's advance on the path and rotating it to the tangent; `Session` re-lays out
  attached text after every edit, so it follows the path, and detaches it (in place) when the
  path object is deleted.
- Fonts: SIL OFL 1.1 fonts bundled unmodified in `crates/openstitch-design/fonts/` (Lato Bold,
  Pacifico), embedded with `include_bytes!`; no Brother font or asset is used.
- Limits: 2000 characters, size 1–300 mm, laid-out text at most 2000 mm in each direction.
  Characters the font lacks are skipped and reported (`missing`).
- User fonts (`openstitch_design::fonts`): `fonts.loadTrueType` reads a TrueType/OpenType file
  or one face of a collection from a path the user gives (sandboxed like every file command)
  and stores it, unchanged and base64-encoded, in `Design::fonts`, so the `.osd` reopens
  without the file. Text objects name it by id like a bundled font (bundled ids win). The
  bytes are an `Arc`, so undo snapshots share them. Font files are hostile input: at most
  24 MiB; a collection header must list at most 64 faces whose offsets lie in the file; every
  table of the chosen face must lie inside the file (ttf-parser would silently drop truncated
  tables); the font needs a Unicode `cmap` that maps something; parsing and each glyph
  outline run under `catch_unwind` (one ttf-parser assertion panics on bad collection
  offsets). A glyph over 20 000 outline segments counts as missing and a laid-out text over
  600 000 segments is refused. A design holds at most 16 fonts and 40 MiB of them; `.osd`
  files re-check all of this on open.
- Embroidery fonts (`FontData::Embroidery`, file format in FILE_FORMATS.md → OpenStitch font):
  glyphs in 0.1 mm at the font's own size, +y down, origin on the baseline at the left set
  line. A glyph may hold outlines (sewn like TrueType glyphs, with the text's sewing) and/or
  a stitch block (user-mapped text: a registered embroidery pattern, sewn as is). Layout
  scales stitch glyphs with the size like outlines and joins them into the text object's
  `stitch_block` (trim + colour change between glyphs). The compiler sews a text's
  outlined glyphs letter by letter, then its stitch glyphs. Bounds and hit-testing include
  the stitch glyphs. `text.toShapes` turns them into one stitch pattern object.
  `fonts.mapCharacter` places a pattern's box on the baseline at the left set line, moved by
  `dx`/`dy`; the width defaults to the pattern's. `fonts.mapFiles` takes characters from file
  names after PE-DESIGN's multiple-import rule (u_A, l_a, s_bs …) plus single-character
  names and `U+XXXX`, and skips patterns outside 5–500 mm.
- Font Creator works on embroidery fonts in the design, so every step is an undoable command
  and the result is usable by text at once. `fonts.convertTrueType` lays each character out
  with `text::glyph_outline` at the font's standard height, so a converted glyph matches the
  TrueType text exactly (blank glyphs keep their width). `fonts.editGlyph` puts a glyph on
  the page as a fill shape with its left set line at `x` and baseline at `y`; after point
  edits, `fonts.setGlyph` with the same `x`, `y` stores the selected outlines back (the
  width is kept unless `advance` is given). Glyphs are drawn at the standard height:
  changing it with `fonts.setMetrics` rescales how text sizes them, not the drawings.
- Characters from an image (`font_images.rs`, digitize feature): the image is thresholded
  (inverted when ink fills most of the border), split into 4-connected components
  (`regions::components`) and specks under `minArea` dropped. Split mode groups components
  into rows (a component joins the row whose extent holds its centre) and, within a row,
  merges components overlapping horizontally by half the narrower one (dots, accents, "=");
  each row's baseline is the median bottom of its characters. Fitted characters share one
  scale (the tallest character, or `capPixels`, spans the standard height) with a 4 % left
  bearing and width = outline + 8 %; whole mode on the background image with `x`, `y` uses
  the image where it is placed, like `fonts.setGlyph`. Tracing is `regions::trace_mask`, as
  Auto Punch. `fonts.traceImage` is the read-only preview the editor shows for assignment.
- Monograms (`openstitch_design::monogram`): one group per monogram, the frame sewn first.
  Block and Script letters are text objects placed side by side, with the middle letter full
  height, the sides at 70 % and Script overlapping. Diamond and Circle letters are glyph
  outlines stretched into vertical bands (each as tall as the silhouette at its inner edge)
  and intersected with the silhouette (`boolean::combine`), so they are shapes. The first
  letter keeps the `MonogramSpec` (letters, style, font, height, frame, margin, aspect,
  centre; the centre moves with transforms), which `monogram.edit` uses to rebuild the group
  in place with the same threads. Frames are drawn from geometry (Bézier ellipses, polygons,
  leaves) so their inner edge clears the corners of the letters' box plus the margin.
- Name Drop: `TextSpec::name_drop` holds a box in laid-out coordinates (before the text's
  placement transform, so moves and rotations carry it along). Layout lays the text out
  untransformed, fits its bounds into the box (uniform scale and alignment, or a stretch),
  then applies the transform. Turning the attribute on resets letter and line spacing and
  takes the text's current box, so nothing moves. The list's columns are the Name Drop
  texts in sewing order. `nameDrop.export` lays out, compiles and encodes every row in
  memory before writing `<name>001.<ext>` … (3-digit counter as in PE-DESIGN; base names
  are refused if they contain path separators). CSV is RFC 4180, UTF-8 (BOM allowed),
  1 MiB / 500 rows at most.
- Templates follow PE-DESIGN, where a template is a design whose Name Drop texts are the
  editable slots. `template.open` replaces the design (one undo step), so the canvas is the
  wizard's preview. `template.fill` sets slots by label or in order through the same path as
  `nameDrop.apply`, so a replacement fits the slot's box. `template.list` reads at most 500
  `.ostemplate` files from a folder and its category subfolders, each through the sandbox,
  and reports damaged ones instead of failing.
- Scripts and shaping (`openstitch_design::shaping`): each line is split into level runs by
  the Unicode Bidirectional Algorithm (`unicode-bidi`, UAX #9) and put in visual order, then
  into script runs (`unicode-script`; Common and Inherited characters join the run before
  them). TrueType/OpenType runs are shaped by `rustybuzz` (HarfBuzz's algorithm in safe Rust):
  GSUB/GPOS contextual forms (Arabic, Syriac, N'Ko joining), Indic and Southeast Asian
  reordering, mark positioning, Unicode composition of base + accent, mirrored brackets in
  right-to-left runs. Standard and contextual ligatures (`liga`, `clig`) are turned off so each
  letter stays its own glyph for digitizing and per-character edits; required ligatures stay.
  Kerning (`kern`) follows `TextSpec::kerning` (off by default, so files written before it
  existed lay out unchanged; unkerned text is shaped without the font's legacy `kern` table,
  which works around a rustybuzz 0.20.1 bug that left such right-to-left text in logical
  order). Glyph clusters keep the index of their first character
  (`Glyph::index`). Shaper panics on damaged fonts are contained: that run falls back to one
  glyph per character. Embroidery fonts are not shaped: their characters are set one after
  another in bidi order with their own advances, and scripts that need shaping are named in
  the `shaping` result. Size follows PE-DESIGN 11 (measured with Lato Bold in
  `compat/reference/text`): for TrueType/OpenType fonts it is 0.7 of the em, so Latin capitals
  come out about the size (Lato Bold's H is 1.033 × size), and 100 % line spacing sets lines
  the font's Windows ascent (`OS/2 usWinAscent`) apart. Embroidery fonts keep their standard
  character height as the size. Texts from `.osd` files before version 3 (and templates
  before version 2) carry `metrics: "capHeight"`: size is then the capital height (fonts
  without Latin capitals use 70 % of the em) and 100 % the font's line height, as before.
- Vertical text (`TextSpec::direction`): characters run top to bottom in logical order (no bidi
  reordering), shaped top-to-bottom so `vert` forms and `vmtx`/`VORG` metrics apply (without
  `vmtx`, a cell is ascender − descender with the glyph centred); lines become columns from
  right to left, one line height apart; alignment is top / middle / bottom about y = 0. Text on
  a path is always laid out along the path.
- Per-character edits (`TextSpec::characters`, `text.setCharacter`): offset (mm), clockwise
  rotation about the letter's middle (half its capital height above the baseline) and a size
  that scales the glyph about the middle of its advance on the baseline and scales its advance,
  so later letters move. Edits are keyed by character index, dropped when the text gets
  shorter, cleared by Name Drop, and omitted from the `.osd` when there are none.

## Data type conversions

PE-DESIGN has three kinds of pattern: shape, text and stitch. Shape → stitch already happens
in the compiler; the conversions are engine commands (`crates/openstitch-engine/src/convert.rs`)
and the editor's Convert menu (`convert_ui.rs`, requests in `editor::conversions`).

- `object.toStitches`: every selected shape or text, plus its group members and text on a
  selected path (or the path of a selected text), becomes a stitch pattern holding exactly the
  needle points it sews now (`Compiler::compile_object`: the object compiled inside its
  design, so hole sewing still applies). The object keeps its id, name and group; objects that
  sew nothing are deleted.
- `object.toShapes` (approximation of "Convert to Outline" / "Convert to Blocks"):
  `openstitch_digitize::coverage` draws the sewn segments as 0.4 mm strokes on a 0.1–0.3 mm
  grid, closes gaps narrower than the fill row spacing (chamfer dilate then erode), traces each
  covered area with marching squares and reports its main stitch direction (length-weighted
  doubled-angle mean), median stitch length and thickness. `whole` makes one fill shape in the
  first thread, `parts` one per thread, `blocks` one per covered area of each colour block,
  satin when its stitches span it (median length ≥ 0.7 × thickness, at most 10 mm) and fill
  otherwise, sewing in the stitches' direction. Several shapes are grouped; the stitch pattern
  is replaced in place, so sewing order holds. Grids are capped at 4 M cells (coarser cells for
  big patterns) and 2 M segments.
- `object.regionToLine`: region sewing is removed and the outline is sewn with a running
  stitch in the region's thread.
- Text → shapes is `text.toShapes` (Lettering).
- **Stitch pattern editing** (`openstitch_design::stitch_edit`, commands in
  `crates/openstitch-engine/src/stitch_edit.rs`): needle points are the `Stitch` and `Jump`
  entries of a `StitchBlock`, addressed by index (`stitches.points` lists them with colour
  block). `movePoints`, `setPoint`, `insertPoint` (on the line into a point; `jump` makes that
  line a jump), `deletePoints` (a deleted jump end takes its trims with it, joining the
  stitches), `splitAt` (not at entry/exit; both parts keep the point), `connect` (the later
  pattern continues from the earlier one's exit and takes its colour), `divideByColor`,
  `splitArea` (points inside an outline become a new pattern sewn last). One filter re-links
  any subset of entries: a stitch whose previous needle point was left out starts with a jump,
  colours are re-inserted, trims stay with their point. In the editor the Point tool on a
  selected stitch pattern selects needle points (click, Shift+click, marquee), drags them (one
  `movePoints`), deletes them and inserts on a double-clicked line (`editor/tools/needles.rs`);
  the Stitches menu runs divide, split at point, connect and split off area (drawn with the
  polygon tool). Screenshot: [rust-editor-needles.png](images/rust-editor-needles.png).

## Digitizing

`openstitch-digitize` turns images into design objects. PE-DESIGN's Auto Punch, Photo Stitch
and Design Center are specified only from the public guide; decompiling them is forbidden, so
every algorithm below is this project's own and documented as an approximation (never
Verified Compatible).

- **Hostile input.** Files over 32 MiB, sides over 8192 px or more than 16 Mpx are refused;
  the size is read from the header before any pixel memory is allocated, and the decoder's
  allocation limit is set too. Each conversion then works on a capped grid (Auto Punch at most
  2048 px per side, 5000 regions; Cross Stitch 160 000 cells; Photo Stitch 400 000 samples)
  and at most 500 000 needle points.
- **Colours.** Weighted median cut to N box colours; each box maps to its nearest PEC chart
  thread (red-mean distance); boxes with the same thread merge. Pixels are classified against
  the box colours. "Skip background" leaves out the thread covering more than half of the
  image border.
- **Auto Punch.** Majority smoothing (3×3), 4-connected regions, regions under the minimum
  area merged into the neighbour with the longest shared border, marching squares on pixel
  centres (saddles split, so outlines match 4-connectivity; holes come out as inner
  contours), Douglas–Peucker, then optional least-squares cubic fitting per segment (tangents
  from neighbouring vertices, corners above 55° kept sharp, three Newton reparameterisation
  rounds; a curve wherever the points are not straight and it fits within the tolerance, at
  least one pixel). A region is satin when its longest stitch
  across its principal axis would be at most `satinMaxWidth`, otherwise fill along the axis.
  Colours sew largest area first.
- **Cross Stitch.** The image's colours are reduced first; each cell of a square grid
  (1–10 mm) takes the thread most of its pixels have (transparent cells stay empty). Each colour is one stitch object; each run of cells in a row is sewn "/"
  going right and "\" coming back, stepping along the shared cell sides.
- **Photo Stitch.** *Fill* (after Photo Stitch 1): a grid of row spacing × stitch length is
  error-diffused onto the threads plus the fabric colour; fabric cells stay unsewn, so tone
  becomes coverage; rows are staggered by thirds. *Lines* (after Photo Stitch 2): zigzag rows
  whose swing follows darkness (mono) or the local share of each thread (colour); light areas
  break the line. Lighter threads sew first. Mono stretches contrast first (2nd–98th luminance
  percentile).
- **Design Center** in PE-DESIGN's four stages: (1) line image: luminance below a threshold;
  (2) figure lines: Zhang–Suen thinning, skeleton traced between end points and junctions
  (branches counted as contiguous neighbour groups, so diagonal steps are not junctions),
  closed loops where there are none, short spurs dropped, simplified and curve-fitted;
  (3) figure regions: areas between lines that do not reach the image border, coloured by
  their mean image colour; (4) sew settings: one line object (running, triple or zigzag with
  the measured stroke width) and one shape per region (auto: fill unless near white).
- **Commands** (engine feature `digitize`, on by default): `digitize.autoPunch`,
  `digitize.crossStitch`, `digitize.photoStitch`, `digitize.lineImage` (stage 1, optional PNG
  output through the sandbox's write roots), `digitize.figure` (stages 2–3, read-only, mm),
  `digitize.designCenter` (all stages). The image is read through `EngineState::resolve`, placed
  by `x`/`y`/`width` (default: 80 % of the Design Page, centred), and every conversion is one
  undo step. Tests: `crates/openstitch-digitize/tests/*.rs` (synthetic images, exact region
  and cell counts, colours, contours inside bounds, hostile images) and
  `crates/openstitch-engine/tests/digitize.rs` (undo, sandbox, `bad_digitize_parameters_fail_cleanly`).
- **Programmable Stitch Creator.** Options ▸ Programmable Stitch Creator, a full window (`creator_ui.rs`, model
  `openstitch_app::editor::creator`): edits an `openstitch.pattern` (fill/stamp tile, motif or
  decorative row) on its unit box with snapping; motif ends stay at (0, 0) and (1, 0) and
  decorative row ends move together, so every edit stays valid. The preview compiles a small

## Pattern wizards

PE-DESIGN's pattern wizards (guide: Tutorials 8 and 9-1…9-3) are engine commands
(`crates/openstitch-engine/src/wizards/`) that build ordinary, editable shape objects, so a
wizard is one undo step and its result can be edited like anything else. Behaviour follows the
public guide; geometry is this project's own (offsets and booleans from `boolean`, clipping
and ordering from `paths`) and is an approximation until it can be compared with PE-DESIGN.
The patterns' footprint is the outer boundary of each closed outline (letter counters
included), widened by half the width of wide line sewing; open lines and stitch patterns
count as their bounding box plus 0.5 mm.

- **Background fill** (`wizard.backgroundFill`): fills a closed shape (`area`) or the hoop
  (Design Page without one) around the patterns, as one object sewn before them. *Echo
  clipped*: copies of the footprint offset by `spacing`, 2 × `spacing`, … (rounded), clipped
  to the area. *Echo*: rings `spacing` apart between the area outline and the footprint,
  starting `spacing` from both. *Crosshatch / stripes*: lines `lineSpacing` apart at `angle`
  (and `angle` + 90°), clipped to the area minus the gap. *Link echo ends* joins consecutive
  pieces with a straight run when it stays inside the fill area and is at most twice the
  spacing. *Stippling* and *decorative fill* are a shape with those region types over the area
  minus the gap; `skipOverlap: false` fills the whole area instead.
- **Appliqué** (`wizard.applique`): one line object per stage, grouped, in this order:
  material (running, or `cutting` on the cutwork needles with uncut bridges, or none),
  position (running), tack-down (zigzag / E / V, or none), cover (zigzag / E / V / chain). The
  outline is the patterns' closed outlines (`output: "replace"`, which deletes them; holes
  kept unless `holes: false`) or their footprint offset by `distance` (`"add"`, inserted
  before the patterns so they are sewn on top). Stops: the material, position and tack-down
  threads take the cover colour but are named **"Appliqué material"**, **"Appliqué
  position"** and **"Appliqué tack-down"**, so each stage is its own colour block and the
  machine stops before the next (cut-out, place the fabric, trim).
- **Embroidered patch** (`wizard.patch`): after the patterns, a zigzag (satin) border whose
  inner edge is `distance` from the footprint (centre line at `distance` + `width` / 2,
  rounded offset, outer boundary only), then the cutting line `cutDistance` outside the
  border's outer edge (or outside the footprint with no border): running, on a thread named
  **"Patch cutting line"** (its own colour block, so the machine stops first), or `cutting`
  on the cutwork needles with uncut bridges.
- **Cutwork** (`wizard.cutwork`): the selected closed shapes or text (not both; outlines
  must not cross themselves) are replaced by one group sewn in this order: stabilizing run
  1 mm outside the cut, the cutting line on the outline, a run 0.5 mm outside securing the
  water-soluble stabilizer, net fill (pattern 1–5 = square, diamond, triangle, honeycomb,
  star) over the cutout grown by a quarter of the satin width so it is anchored under it, a
  zigzag underlay (0.6 × width, 1 line/mm) and the covering satin. The cutwork machine
  protocol is not public, so cutting is written as ordinary stitch data:

  | Colour block thread name | Meaning |
  |---|---|
  | `Cutwork needle 1 (0°)` … `Cutwork needle 4 (135°)` | Cut segments for the needle whose blade angle is closest to the segment's direction; each needle is its own block, so the colour change before it is the stop where the machine changes needle |
  | `Cutwork cutting line` | `cutting: "running"`: a line sewn to cut by hand |
  | `Appliqué material`, `Appliqué position`, `Appliqué tack-down`, `Patch cutting line` | Appliqué and patch stages (above) |

  Every other stage keeps the chosen thread, so a stop happens exactly where the thread name
  changes: before cutting, between needles, and after cutting (to lay the stabilizer).
- **Editor.** Design ▸ Background Fill… (`pattern_wizard_ui.rs`, model
  `openstitch_app::editor::pattern_wizards`) applies to the selected patterns; OK sends the one
  command and selects the result. Design ▸ Appliqué Wizard…, Embroidered Patch… and Cutwork Wizard… likewise.
  `--wizard background|applique|patch|cutwork [--apply]` opens (and
  applies) one for scripted screenshots:
  [rust-editor-background-fill.png](images/rust-editor-background-fill.png),
  [rust-editor-applique.png](images/rust-editor-applique.png),
  [rust-editor-patch.png](images/rust-editor-patch.png),
  [rust-editor-cutwork.png](images/rust-editor-cutwork.png).
  Examples: `examples/background-fill.json` →
  [engine-background-fill.png](images/engine-background-fill.png); `examples/applique.json` →
  [engine-applique.png](images/engine-applique.png) (top row: the heart after the position,

## Engine-first layering (after PhotoCraft)

PhotoCraft (github.com/storytold/photocraft, Apache-2.0/MIT) is an independent reimplementation
of Photoshop in Rust, used here as an architectural reference. Principles adopted:

```text
openstitch-app (egui) <-- loopback socket <-- stitchtool connect / openstitch-mcp --live
        |                     stitchtool exec   stitchtool serve (JSON lines)   openstitch-mcp
        |                           |                       |                          |
        +---------------------------+-----------------------+--------------------------+
                                     |
                         command registry (id + JSON params)
                                     |
                       Session: design + undo/redo history
                                     |
          openstitch-design (model, generators, compiler)   openstitch-formats (codecs)
                                     |
                              openstitch-core (stitch stream, threads)
```

- **One registry.** Every editing action is a `CommandSpec` with an id, summary, parameter docs,
  an effect (`read`, `edit`, `file`, `history`) and a run function. The app, CLI, control channel,
  tests and the MCP server all dispatch through `Session::execute`.
- **Untrusted input at the boundary.** Parameters are validated (type, range, finiteness, counts).
  Bad input returns `CommandError` and leaves the document unchanged. `bad_parameters_fail_cleanly`
  is the adversarial suite; extend it with every new command.
- **One history step per edit command**, rolled back on failure. Read and file commands never
  create history.
- **Dependency direction:** core ← formats, design ← engine ← apps. Nothing below the engine
  depends on UI.
- **Control channel:** `stitchtool serve` speaks newline-delimited JSON on stdio. Requests are
  `{"id", "command", "params"}`; replies are `{"id", "ok", "result" | "error"}`; lines are capped
  at 1 MiB. It is for trusted local scripts and has no file roots. The running editor speaks the
  same protocol over a loopback socket; see [Automation socket](#automation-socket-live-editor).
- **MCP server (`openstitch-mcp`).** Newline-delimited JSON-RPC 2.0 on stdio, no network
  listener. Lifecycle: `initialize` (protocol version negotiated from 2025-11-25, 2025-06-18,
  2025-03-26, 2024-11-05; unknown requests get the newest), `notifications/initialized`, `ping`,
  `tools/list`, `tools/call`. JSON-RPC batches (arrays) are refused, as MCP dropped them in
  2025-06-18.
  - *Tools are generated, not hand-written.* One tool per `CommandSpec`, named `id` with `.` → `_`
    (clients and the Claude API accept `[A-Za-z0-9_-]{1,64}`). The input schema comes from the
    `ParamDoc` kind strings (`mm`/`degrees`/`factor` → number, `int a-b` → bounded integer,
    `a|b|c` → enum, `color` → string or integer, `[[x, y]] mm` → array of pairs, `ids` → `ids`
    array or `id`). Effects map to annotations (`read` → readOnlyHint, `file` → destructiveHint).
    Schemas guide the model; `Params` still validates every value.
  - *Errors.* Unknown tools and malformed `tools/call` params are JSON-RPC errors (-32602);
    command failures (bad parameters, missing objects, refused paths) are tool results with
    `isError: true`, so the model can read and correct them.
  - *`run_batch`.* Up to 256 steps (`{tool, arguments}`), all checked before any runs (unknown
    tool, nested `run_batch`/`preview`, bad shapes → nothing happens). Stops at the first failing
    step unless `continueOnError`; finished steps stay done, each edit its own undo step. Not
    transactional, since file writes cannot be rolled back.
  - *`preview`.* Compiles the design and draws the Design Page plus sewn runs in thread colours
    into a PNG (tiny-skia), longest side 64–2048 px; returned as an MCP `image` content block with
    the stitch statistics as text.
  - *File roots.* The engine `Sandbox` confines every command that touches a file
    (`stitches.import`, `project.open`: read; `design.export`, `project.save`: write; the
    `library.*` Design Database commands, see [Design Database](#design-database)), including
    ones added later through `EngineState::resolve`. Write roots are readable; read roots are
    read-only; no roots means no file access. Refused: `..` components, absolute paths outside
    the roots, and paths whose real location (symlinks resolved on the file if it exists, else on
    its parent directory, which must exist) is outside. Roots are canonicalised at startup. Known
    limits: a process that can change the filesystem concurrently could race the check, and hard
    links are not detected.
  - *Capabilities.* Every command needs a set of capabilities derived from its effect —
    `edit` (edits and undo/redo), `writeFiles` (file commands), plus `readFiles` for the edit
    commands in `capabilities::FILE_READING_COMMANDS` and the Design Database commands in
    `LIBRARY_READING_COMMANDS` (`library.list` / `info` / `search` are reads, so `--read-only`
    keeps them; convert, catalogue and copy also write) — reported by `commands.list` as
    `requires`. `Session::set_capabilities` limits a client: `--read-only` (inspect, measure,
    preview; no edits, history or file writes) and `--no-files` (no file access; refused
    together with roots). Not-permitted tools are left out of `tools/list` and refused by
    `tools/call` and `run_batch`; the engine refuses them at dispatch and again in
    `EngineState::resolve`, so a file command missing from the list still cannot open a path.
    `stitchtool serve` takes the same two flags.
  - *Size caps.* The stdin reader never buffers more than 1 MiB of a line; longer lines are
    dropped as they stream and answered with -32600. JSON nested deeper than 64 levels is refused
    before decoding. A reply over 8 MiB is replaced by a -32603 error with the same id. Batches
    are capped at 256 steps, previews at 2048 px; the engine caps imports at 64 MiB and point
    lists at 100 000.

## Automation socket (live editor)

`openstitch --listen PORT` lets external tools drive the session of the editor that is open on
screen, with the same JSON requests and per-command capabilities as `stitchtool serve`.
`stitchtool connect` forwards stdin lines to it; `openstitch-mcp --live` sends every tool call to
it (the `preview` tool, which renders the MCP server's own design, is refused in that mode).

```text
client --TCP 127.0.0.1--> connection thread --mpsc Job--> UI thread (EditorApp::serve_remote)
       <---- reply line --                   <--reply----    Policy::apply → Session → restore
```

Protocol: one JSON object per line each way. Requests are
`{"token", "id"?, "command", "params"?}`; replies are `{"id"?, "ok": true, "result"}` or
`{"id"?, "ok": false, "error"}`, exactly `Session::handle`'s.

Security model (`crates/openstitch-remote`):

- **Off by default.** Nothing listens unless the editor is started with `--listen PORT`
  (`0`: an OS-assigned port).
- **Loopback only.** The listener binds `127.0.0.1`, never `0.0.0.0`, and drops peers that are
  not loopback. The client refuses non-loopback addresses, so the token is never sent off the
  machine.
- **Per-launch token.** 32 bytes from the OS random source (`getrandom`), hex-encoded, new at
  every launch. Every request must carry it; it is compared in constant time, and a missing or
  wrong token gets an error and the connection is closed. The editor prints the address, token
  and endpoint file on stderr, and writes `{"address", "token", "pid"}` to `automation.json` in
  the OS config directory (next to `user.json`: `~/Library/Application Support/OpenStitch`,
  `%APPDATA%\OpenStitch`, `$XDG_CONFIG_HOME/openstitch`). On Unix the directory is created
  0700 and the file 0600; it is created exclusively after removing any previous file, so a
  planted symlink is not followed. On Windows the per-user `%APPDATA%` ACL keeps it private.
  The file is removed when the editor exits normally (only if it still holds this launch's
  token); after a crash a stale file just points at a closed port.
- **Same capabilities as `stitchtool serve` and MCP.** `--listen-read-only` (no edits,
  undo/redo or file writes) and `--listen-no-files` (no file access). The engine refuses at
  dispatch and again in `EngineState::resolve`.
- **File roots.** Clients get an engine `Sandbox`: `--listen-root DIR` (read/write) and
  `--listen-read-root DIR` (read only), repeatable. With no roots every file command is refused,
  so a token alone never reaches the disk. The editor's own session keeps full access and no
  sandbox: `Policy::apply` swaps the client's capabilities and sandbox in for one request and
  `Policy::restore` puts the editor's back (`Session::set_sandbox`).
- **Limits.** Request lines over 1 MiB get an error and the connection is closed (the reader
  never buffers more); a connection idle for 5 minutes is closed; at most 4 connections at once
  (more get "too many connections"); a request that waits more than 30 s for the UI thread gets
  a timeout error and is skipped if still queued. Clients cap replies at 64 MiB. Every early
  close (refused connection, wrong token, oversized line) writes the error, half-closes and
  drains the client's unread bytes (at most 1 s / 4 MiB) before dropping the socket: closing
  with unread data sends a TCP reset, which on Windows discards the reply before the client
  reads it.
- **One thread owns the session.** Connection threads never touch the `Session`; they queue a
  `Job` on an mpsc channel and wake egui (`request_repaint`), and `EditorApp::serve_remote`
  drains the queue at the start of each frame. A client's edit is one Undo step in the Edit
  menu, and a client's `history.undo` / `history.redo` act like the menu (a grouped user gesture
  undoes as a whole), so the editor's history stays coherent.

Threat model: this protects against other machines and against other local users. It does not
protect against code running as the same user, which can read the token file (or the editor's
memory) anyway. A request that times out may still run if the UI thread picked it up just
before the deadline.

Tests: `crates/openstitch-remote/tests/socket.rs` (round trip through a test host, wrong and
missing tokens, oversized and invalid lines, read-only and file-root enforcement, timeouts,
connection limit, endpoint file life cycle, loopback-only client),
`openstitch-app` `remote::tests` (shared undo history with the editor),
`openstitch-mcp/tests/live.rs` and `stitchtool/tests/connect.rs`.

## Compatibility harness

`crates/openstitch-compat` checks OpenStitch's behaviour against declared expectations, kept
apart by tier: internal regression, oracle, PE-DESIGN reference, sew-out. The method, the spec
format and the measurements are in [COMPATIBILITY_TESTS.md](COMPATIBILITY_TESTS.md).

```text
compat/specs/<area>/<id>.json --spec--> runner --Session::sandboxed(work/<id>)--> script, exports
                                           |                                         |
compat/reference/ + MANIFEST.json ---------+-- provenance --+                 FileType::read
compat/machine/<record>.json --------------+                |                        |
                                           v                v                        v
                     report.json, summary.md, COMPATIBILITY_STATUS.md <-- checks <-- measure / compare
```

| Module | Role |
|---|---|
| `spec` | The `openstitch-compat/1` model. It validates everything that needs no run: ids, safe relative paths, sources, tiers. |
| `trace` | Stitch streams in mm, from a `StitchPattern` or a `stitches.points` reply. Alignment anchors and geometry helpers. |
| `measure` | The measurements, one JSON value each. |
| `compare` | The semantic comparer: per-block sequence with resync, counts, bounds, threads, metadata, PES object summary, bytes. Origin normalisation. |
| `tolerance` | Unit-tagged tolerances (`mm`, `count`, `deg`, `percent`) and structural checks of expected values, including ranges. |
| `provenance` | Reference files and sew-out records. Size-capped regular files and their own SHA-256 (`sha256`). Nothing counts without a complete record. |
| `runner` | Runs one spec: fresh work directory, inputs copied, the script in a sandboxed `Session`, exports written and read back, checks per tier, the spec's status and tier. |
| `report`, `cli` | Deterministic JSON, the markdown summary, the generated status table, `stitchtool compat` arguments. |

Security follows the engine's rules:

- Scripts run in `Session::sandboxed` on the spec's own work directory.
- Spec, reference and record paths must be relative, with no `..`.
- Spec files are capped at 1 MiB, and reference files, records and inputs at 32 MiB.
- Symlinks are not followed.
- The harness never launches another program.

Tests: `tests/comparer.rs` (synthetic patterns that differ in one known way, tolerance edges,
the oracle fixtures), `tests/runner.rs` (pending references, provenance, tier rules, sew-out
records, invalid specs, sandboxing, determinism, the stale-table check) and
`tests/repo_specs.rs` (the repository's specs pass and the committed table is current).

## Desktop editor (`crates/openstitch-app`)

```text
main.rs   app.rs (state, menus, shortcuts, files)   canvas.rs   panels.rs   script.rs
   egui widgets and painter only; pointer → model units; CommandRequest → Session::execute
                                     |
openstitch_app::editor (lib, no egui, unit-tested)
   viewport · hit · handles · tools (ToolController, ClickCounter) · points · pen
   render (RenderModel, PatternStats)
   inspector (InspectorModel, PEC palette) · objects (rows, reorder) · request (CommandRequest)
                                     |
                       openstitch-engine Session (the only writer)
```

- **Edits only through the registry.** Tools and panels build `CommandRequest`s; `EditorApp::execute`
  runs them with `Session::execute` and recompiles the design after every `edit`/`history`
  command. The app keeps view state only: selection, viewport, simulator position, inspector
  drafts. File actions are commands too (`project.open`/`project.save`, `stitches.import`,
  `design.export`); opening a machine file reads it once with `openstitch-formats` only to size the
  Design Page before `design.new` + `stitches.import` + `object.center`.
- **One gesture, one Undo.** A drag changes nothing until release (the canvas draws the
  `ToolPreview`), inspector number fields keep a draft while dragged or typed and send one command
  when released. When a user action needs several engine steps, `EditorApp::grouped` records them
  as one entry and Undo/Redo run `history.undo`/`history.redo` that many times. Edits that change
  nothing record no step.
- **Point and Pen tools.** `editor::points` hit-tests vertices, curve handles and the nearest
  segment with its parameter *t* (exact projection on lines; 48 samples plus golden-section search
  on cubics, so *t* is the Bézier parameter `object.insertPoint` takes), and mirrors
  `object.setPoint` / control moves for the drag preview. The Point tool edits the one selected
  shape: a vertex drag sends one `object.setPoint`, a handle drag one `object.setSegment` with
  both control points, a double-click on a segment one `object.insertPoint`, Delete one
  `object.deletePoint`; C / S curve or straighten the segment under the pointer (new handles
  follow Catmull-Rom tangents through the neighbouring vertices). `editor::pen` keeps the path
  being drawn as anchors with an optional out-handle (the in-handle mirrors it); click = corner,
  click-drag = smooth, clicking the first anchor closes, Return (or double-click) finishes open,
  and the whole path is one `shape.path` with `curves`. Double-clicks are counted by
  `ClickCounter` (0.4 s, 6 pt) so tools see `PointerEvent::clicks` on the press. Outlines are drawn
  from `Contour::path()`, so curves render flattened to 0.05 mm. Screenshots:
  [rust-editor-points.png](images/rust-editor-points.png),
  [rust-editor-pen.png](images/rust-editor-pen.png).
- **Corner scaling.** `object.scale` and `object.rotate` take `originX`/`originY` (the opposite
  handle); `CommandRequest::scale_about` detects them through the registry's `ParamDoc`s and sends
  one command, so a corner drag is one engine step.
- **Rendering.** `RenderModel::build(pattern, limit)` turns the compiled stream into polylines
  per colour block (a stitch sews from the previous position, a jump is travel, trims and colour
  changes break strokes) and stops after `limit` stitches for the simulator; it is rebuilt only
  when the design revision or simulator position changes. egui tessellates the polylines on the
  GPU through wgpu. Thread is drawn thinner than real (2.5 × scale, 0.5–3 pt) so rows stay visible.
- **Travel vs sewn.** A move is drawn as thread only if it is a `stitch` and the thread has not
  been cut since the last stitch; jumps and the first move after a trim or colour change are
  travel and can be dimmed or hidden.
- **Window chrome.** The command layout is data in `editor::ribbon` (every command is an
  `Action` with label, ScreenTip, shortcut, engine command and availability; tabs, groups,
  contextual-tab rules, Application and Option menus, Quick Access Toolbar defaults) and
  `editor::prefs` (theme, Quick Access Toolbar, panes docked/floating/hidden, recent files,
  saved as `ui.json` beside `user.json`). The binary's `ribbon.rs` draws it, decides which
  commands are enabled for the selection and runs them; `panes.rs` holds the Sewing Order,
  Import/Color/Sewing Attributes/Text Attributes and Stitch Simulator panes and the status bar;
  `icons.rs` renders the command icons (SVGs in `assets/icons/commands`, with code-drawn
  fallbacks); `theme.rs` the light (default), dark and system themes. See
  [UI_LAYOUT.md](UI_LAYOUT.md).
- **Input.** Scroll pans, pinch or Ctrl/⌘+scroll zooms at the pointer, middle-drag, Space+drag or
  the Pan tool (H) pans; ⌘/Ctrl+C / V copy and paste objects, ⌘/Ctrl+= / − zoom; ⌘/Ctrl+Z, ⇧+⌘Z / Ctrl+Y, ⌘S, ⇧⌘S, ⌘O, ⇧⌘I (import), ⌘N, ⌘0 (fit), ⌘A, ⌘D, Delete,
  arrows (0.1 mm, Shift 1 mm), V/A/R/E/P/B tools (select, point, rectangle, ellipse, polygon,
  pen), Return closes a polygon or finishes a pen path, Esc cancels; with the Point tool Delete
  removes the selected vertex and C / S curve or straighten the segment under the pointer.
- **Scripted runs.** `--script` feeds pointer and key events through eframe's `raw_input_hook`,
  in model millimetres (`drag:10,10,40,30;type:e;cmd+key:Z`) or window points (`sclick:x,y`), so the
  real canvas, tool, panel and shortcut code runs; `--screenshot out.png` captures the frame
  after the script (`--demo`, `--select`, `--simulate`, `--zoom`, `--size` set the scene;
  `--ribbon TAB`, `--pane TAB`, `--theme`, `--show appmenu|property|shortcuts|floating|print` set the
  chrome; screenshots ignore the saved window preferences). `python3 tools/screenshots.py`
  rebuilds the editor screenshots from examples/ in a temporary folder with a stand-in home
  folder, so no local path shows, and downscales and quantises them. The
  images in `docs/images/rust-editor-*.png` are made this way on macOS (Metal).

## Decisions

- **Rust on every platform (2026-10-18).** The goal is support for all operating systems, so the
  engine and UI are Rust: one codebase, one UI toolkit, CI on macOS, Windows and Linux.
- **No MCP SDK dependency.** The stdio server needs five methods; implementing them directly keeps
  the security-relevant parts (size caps, path checks, error mapping) in this repository and
  tested. Revisit if HTTP transport, sampling or elicitation is needed.
- **Tests compare against fixtures from an independent implementation** (pyembroidery) now, and
  against PE-DESIGN reference fixtures once a licensed installation is available.
- **Round half to even** for coordinate rounding, matching the reference fixtures.
- **Commands take millimetres and degrees**; the model stores 0.1 mm (machine units), so
  conversion happens once, at the boundary.
- **`ttf-parser` for font outlines (2026-10-19).** Lettering needs TrueType/OpenType glyph
  outlines. `ttf-parser` (MIT OR Apache-2.0, RazrFalcon/harfbuzz org) is pure safe Rust,
  zero-allocation and zero dependencies, parses `glyf` and `CFF`/`CFF2` outlines, and is
  heavily fuzzed as the parser under `rustybuzz`, `resvg` and `cosmic-text`. It is built with
  `default-features = false, features = ["std"]`. Rasterizing
  crates (`fontdue`, `ab_glyph`) were not used: they target pixels, and the engine needs exact
  vector outlines; writing a parser in-house would add an untrusted-input attack surface.
- **`rustybuzz` and `unicode-bidi` for shaping (2026-10-19).** Right-to-left and complex
  scripts need OpenType shaping and the bidi algorithm. `rustybuzz` 0.20.1 (MIT; a port of
  HarfBuzz's shaping algorithm to safe Rust, built on the `ttf-parser` 0.25 already in use)
  and `unicode-bidi` 0.3.18 and `unicode-script` 0.5.8 (MIT OR Apache-2.0, servo / unicode-rs)
  are pinned exactly. HarfBuzz itself would need C FFI, which the workspace forbids; writing a
  shaper in-house would not get near its script coverage. Their dependencies (`bitflags`,
  `bytemuck`, `smallvec`, `core_maths`/`libm`, `unicode-bidi-mirroring`, `unicode-ccc`,
  `unicode-properties`) are MIT and/or Apache-2.0.
- **`image` for decoding (2026-10-19).** Digitizing needs PNG, JPEG and BMP decoding. `image`
  0.25 (MIT OR Apache-2.0) is pure Rust, already in the lock file through eframe, and exposes
  header dimensions and allocation limits before decoding, which the hostile-input rules
  need. Only the `png`, `jpeg` and `bmp` features are enabled (`png`, `zune-jpeg`); no
  encoder, no other formats.
- **`i_overlay` for shape operations (2026-10-19).** Merge, remove overlap, union/difference/
  intersection/xor, split along a cut outline and offset lines need robust polygon clipping
  and offsetting. `i_overlay` 9.1 (MIT OR Apache-2.0, the same licence as OpenStitch; iShape-Rust)
  is pure safe Rust, snaps to an integer grid so results are deterministic and robust to
  self-intersections and coincident edges, and is the engine under `geo`'s boolean operations.
  Its dependencies (`i_float`, `i_shape`, `i_tree`, `i_key_sort`) are by the same author under
  the same licence. `geo` itself was not used: it would add the whole GIS type stack for the same
  engine. `clipper2` bindings were rejected (C++ through FFI). Writing a clipper in-house was
  rejected as a large correctness risk. Curved segments are flattened with provenance before
  clipping; afterwards result edges that follow an input curve are restored as exact Bézier
  pieces of it (offsets: of the curve's offset copy), the rest stay straight; the crate needs Rust 1.88, set as `openstitch-design`'s `rust-version` (the workspace keeps 1.85).
  `openstitch_design::boolean` wraps it, so a different engine can replace it in one file.
- **User settings outside designs (2026-10-19).** Attribute sets and user thread charts live in
  one JSON file per user (`openstitch.user` format), loaded by the front end that wants them
  (the desktop app) with `Session::with_user_settings`. Commands that change them have the
  `settings` effect: they need the edit capability, are not undo steps, and the file is written
  (temporary file + rename) before the change takes effect. Automation front ends keep the
  settings in memory unless given a file.
- **Default sewing attributes are placeholders** (fill 2.5 rows/mm, 4 mm stitches; satin
  3 rows/mm; running 2.5 mm) until calibrated against PE-DESIGN output.

## Design Database

`openstitch-library` reproduces PE-DESIGN's Design Database (guide chapter "Design Database")
as a library the editor and the engine's `library.*` commands share. It reads `.osd` projects
through `openstitch_design::project` (the codec moved out of the engine, which re-exports it),
so the engine can depend on the library (feature `library`, on by default, built without the
`system-trash` feature) without a dependency cycle.

- **Engine commands** (`crates/openstitch-engine/src/library.rs`): `library.list` (a folder's
  subfolders and designs with their Property information, paged by `offset` / `limit`),
  `library.info`, `library.search` (the `Query` fields: name wildcards, formats, stitch /
  colour-change / total-colour / width / height / date ranges, PES properties, subfolders),
  `library.convert` (`ConvertOptions`: target format, output folder or next to each source,
  conflict, DST jumps per trim), `library.catalog` (PDF, PNG pages, HTML with its image
  folder, CSV; the catalogue `Setup` fields), `library.createFolder`, `library.rename`,
  `library.copy`, `library.move`. There is no delete command: deleting stays in the app (OS
  trash after the user confirms). `paths` may name folders, which add their design files
  (walked with `subfolders`). Every path goes through `EngineState::resolve`; files found by
  listing or walking are resolved again before they are opened, so a symbolic link to a file
  outside the roots is left out and counted in `outsideRoots`. Rename and move resolve the
  entry's parent folder for writing and act on the entry itself, so a root cannot be renamed
  or moved and nothing is taken out of a read root. Conversions next to their sources need
  the source folder to be writable; the HTML image folder is resolved like the page.

- **Hostile input.** `Limits` caps file size (64 MiB), entries read per folder (50 000), files
  and folders per walk (100 000 / 20 000) and depth (32). Only regular files are opened
  (`metadata` first, so a FIFO or device never blocks), reads use `take(limit + 1)` so a
  growing file is refused, and decoders run under `catch_unwind`. A walk never follows a
  symbolic link to a folder and visits each canonical folder once, so link loops and
  bind-mount cycles end. Unreadable files stay listed with their error.
- **No surprises on disk.** Copies, conversions and catalogues create new files with
  `create_new`; an existing name is skipped or the new file gets a free "name (2)" name, never
  overwritten. Catalogue output replaces files only when the caller passes `overwrite` (after
  asking), through a temporary file and a rename. Moving across drives copies first and
  removes the source only after the copy succeeded. Rename keeps the extension (as in the
  guide) and refuses existing targets except a change of letter case. Delete goes to the OS
  trash after the UI's confirmation.
- **Catalogue pages** are laid out once as a display list in points and drawn by two back
  ends: a PDF writer (Type 1 Helvetica in WinAnsiEncoding, Flate-compressed RGB images at
  150 dpi, no timestamps, so identical input gives identical bytes) and a tiny-skia rasteriser
  that sets text with the bundled Lato font. CSV is RFC 4180 with CRLF; cells starting with
  `=`, `+`, `-` or `@` get a leading apostrophe so spreadsheets do not evaluate them.
